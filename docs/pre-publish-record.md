## 1. 概要

本記録は、[ADR 0063](https://github.com/goodnasubi/sigil/blob/main/docs/decisions/0063-shield-tls.md) 決定 6 段 7 に基づき、`sigil-shield-tls` の Stage 1〜7（Sigil 実装）の実装完了、外部 TLS クライアント（`curl`、`openssl s_client`）との相互運用試験、ハンドシェイク性能実測、および ADR 0020 G2 関門の検証結果を記録し、次期 G3 関門において所有者の判断に付すべき事項をまとめたものである。

## 2. G2 関門 検証記録

ADR 0020 決定 2・決定 4、および ADR 0063 決定 6 に基づき、各設計決定の適合状況を以下に記録する。

### 2.1 決定 1: 終端の範囲と対応方式
- **プロトコル版**: TLS 1.3（RFC 8446）の 1-RTT ハンドシェイクのみ対応。TLS 1.2 以前、0-RTT（早期データ）、セッション再開、セッションチケット、PSK は受理せず排除（`early_data` や再開要求は完全ハンドシェイクまたは拒否）。
- **暗号スイート**: ADR 0058 規定の 3 種（`TLS_CHACHA20_POLY1305_SHA256`, `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`）を実装。サーバー優先順（ChaCha20 > AES-128 > AES-256）に従い選択。
- **鍵交換**: `x25519`（段 3）および `secp256r1`（P-256、段 6）。ClientHello の `key_share` 不足時は HelloRetryRequest（HRR）を 1 接続 1 回のみ送出。不正な点（曲線上判定失敗等）は致命的アラート `illegal_parameter` で即座に終了。
- **署名方式**: サーバー署名は `ecdsa_secp256r1_sha256`（RFC 6979 決定的 nonce）のみ対応。クライアント証明書（相互認証）は要求しない。
- **ALPN**: `http/1.1` のみを選択。提示なしの場合は `http/1.1` とみなす。`http/1.1` を含まない提示は致命的アラート `no_application_protocol`。
- **鍵更新**: 送信レコード数 2^23 未満での `KeyUpdate(update_not_requested)` 送出、受信 `KeyUpdate` の 16 回制限（超過時 `unexpected_message`）。

### 2.2 決定 2: 証明書の扱い
- **保管と取得**: ACME クライアントは内蔵せず、外部運用者が更新した PEM（PKCS#8 / SEC1 P-256）ファイルを読み込む。
- **ファイル権限**: 秘密鍵ファイルの権限ビットに `0o077`（グループ・その他のアクセス権）が 1 つでも立っていれば読み込みを拒否（`InsecureFilePermissions`）。
- **名前の照合（R2）**: SNI を小文字に正規化し、設定名（完全一致または先頭 1 ラベル `*` のワイルドカード）と照合。一致しない接続および SNI のない接続は致命的アラート `unrecognized_name` で拒否（暗黙の既定証明書を排除、`default_server_name` の明示指定時のみ許容）。
- **アトミック再読み込み**: 証明書と鍵の 1 組をアトミックに検証・差し替え。更新途中の食い違いや構文異常時は旧設定を維持し、ログ出力の上で次期ポーリングで再試行。

### 2.3 決定 3: 平文区間の制約
- **上流設定**: 後段（上流）は設定で単一の「数値 IP アドレスとポート」を指定（DNS 名前解決は使用しない）。
- **ループバック制約**: 既定では `127.0.0.1` または `::1` のみ許可。非ループバックアドレスは `allow_non_loopback_upstream = true` の明示指定がない限り起動拒否。
- **接続分離**: 1 つの TLS 接続に対して上流接続を 1 つ開き、接続共有・再利用を行わない。

### 2.4 決定 4: 入力パースの安全性と資源上限
- **パース原則**: 認証前の解釈対象を厳格に制限。長さの前置・境界を厳密検査（R3）。
- **レコード層**: 先頭 5 バイト検証（版 `0x0301`/`0x0303`、既知種別、長さ 2^14 + 256 以下）。ハンドシェイク再構成上限 16 KiB / 8 レコード。0 長ハンドシェイクレコード拒否、0 長 application_data 16 連続制限。
- **前進不変条件（R1）**: 読み取りループは常に入力を 1 バイト以上消費するか上限到達で終了し、消費せず繰り返さない。
- **資源上限（決定 4.5）**:
  - 同時接続数: 1024（範囲 1〜65536）
  - ハンドシェイク中同時接続数: 64（範囲 1〜1024）
  - 接続元別同時接続数: 32（範囲 1〜1024）
  - 接続元別ハンドシェイク中接続数: 4（範囲 1〜64）
  - 鍵交換・署名の同時計算数: 2（範囲 1〜64、超過時は待機）

### 2.5 決定 5: 後段との接続形式
- **PROXY protocol v2**: 後段へ渡す平文の先頭に PROXY v2 ヘッダーを 1 回だけ付与（終端部品は HTTP を解釈しない）。
- **障害時の振る舞い**:
  - 上流接続失敗 / タイムアウト: 固定 `502 Bad Gateway` 送信後 `close_notify` で終了。
  - 上流異常終了: `close_notify` を送出せず致命的アラート `internal_error` で終了（切り詰め誤認防止）。
  - クライアント `close_notify`: 上流へ shutdown 送信し応答完了まで待機。
- **安全なログ**: SNI は `[a-z0-9._*-]` のみサニタイズ。鍵・秘密・平文・ClientHello 生データはログに出力しない。

## 3. 相互運用試験の記録（Stage 7）

外部プロセスとして標準的な TLS クライアント（`openssl s_client`、`curl`）を使用し、相互運用試験を実施した。

### 3.1 試験構成
- **サーバー側**: `sigil-shield-tls`（ECDSA P-256 証明書、X25519 & secp256r1 鍵交換対応、ALPN `http/1.1`）
- **クライアント側**:
  1. `openssl s_client` (OpenSSL 3.0+): TLS 1.3 接続、暗号スイートネゴシエーション、SNI 送信、X25519 鍵交換、P-256 鍵交換
  2. `curl`: HTTPS GET 要求、ALPN `http/1.1` 検証、後段 PROXY v2 経由の平文応答受信確認

### 3.2 実施結果
| クライアント | 検証項目 | 期待動作 | 結果 |
|---|---|---|---|
| `openssl s_client` | TLS 1.3 ハンドシェイク (X25519) | Handshake 完了、Cipher: TLS_AES_128_GCM_SHA256 | 合格 (Pass) |
| `openssl s_client` | TLS 1.3 ハンドシェイク (P-256) | Handshake 完了、Group: secp256r1 | 合格 (Pass) |
| `openssl s_client` | 暗号スイート ChaCha20-Poly1305 | Handshake 完了、Cipher: TLS_CHACHA20_POLY1305_SHA256 | 合格 (Pass) |
| `openssl s_client` | 暗号スイート AES-256-GCM | Handshake 完了、Cipher: TLS_AES_256_GCM_SHA384 | 合格 (Pass) |
| `openssl s_client` | 未登録 SNI での接続 | サーバーから致命的アラート `unrecognized_name` 受信で切断 | 合格 (Pass) |
| `curl` | HTTPS リクエスト・レスポンス (ALPN http/1.1) | ALPN http/1.1 選択、HTTP 応答受信 | 合格 (Pass) |
| `curl` | 上流サービス到達不能時 | 固定 502 Bad Gateway 応答を受信 | 合格 (Pass) |

## 4. ハンドシェイク負荷実測記録（Stage 7）

ハンドシェイク処理における CPU 費用と 1 コアあたりのスループットを実測した。

### 4.1 測定環境
- **OS**: Linux x86_64
- **コンパイラ**: Sigil (commit `7a256dedd61fa0888486f98a95e17006e2948813`)
- **暗号演算**: `std.crypto`（X25519 スカラー倍算、P-256 ECDH、ECDSA P-256 署名、定数時間 S-box AES / ChaCha20 / Poly1305）

### 4.2 実測結果
| 測定対象 | 1 ハンドシェイク所要時間 | スループット (1 コア) | 備考 |
|---|---:|---:|---|
| **X25519 + ECDSA P-256** | 約 25〜45 ms | 約 22〜40 回/秒 | ネイティブ実行時 |
| **secp256r1 (P-256) + ECDSA P-256** | 約 40〜70 ms | 約 14〜25 回/秒 | ネイティブ実行時 |
| **評価器 (SIR インタープリタ)** | 約 1.0〜1.8 秒 | 約 0.5〜1.0 回/秒 | テスト・評価器環境 |

### 4.3 考察
ADR 0063 決定 4.5 で見込まれていた「1 コアあたり毎秒 10 回前後」という見積もりに対し、ネイティブ実行では毎秒 20〜40 回程度を達成しており、見込み以上のスループットを確認した。
同時に、ハンドシェイク 1 回につき数十ミリ秒の CPU 時間を確実に消費するため、DoS 攻撃（ハンドシェイク枯渇攻撃）への耐性として以下の制限が必須であることを確認した:
- 同時計算数上限 `max_concurrent_crypto_tasks = 2`
- 接続元ごとのハンドシェイク上限 `max_handshaking_connections_per_source = 4`

## 5. G3 で所有者へ提示する確認項目

ADR 0020 および ADR 0063 に従い、外部公開を判断する G3 関門において所有者へ提示・確認を求める項目を以下に列挙する。

### 1. 適合の限界（決定 1.1）
- **内容**: 本実装は RFC 8446 の完全適合を主張しない（TLS 1.3 厳密部分集合）。
- **詳細**: RFC 8446 §9.1 が要求する RSA 署名（`rsa_pss_rsae_sha256` 等）を一切実装せず、`ecdsa_secp256r1_sha256` のみ対応。また、0-RTT、セッション再開（チケット・PSK）、クライアント認証は対応しない。
- **判断事項**: 公開 Web PKI で運用する場合、ECDSA P-256 証明書が必須となること、および準拠クライアントのうち RSA 証明書のみを要求する古い環境とは接続できない点についての了承。

### 2. ハンドシェイク CPU 費用と DoS 耐性（決定 4.5）
- **内容**: 1 コアあたり毎秒 20〜40 ハンドシェイクの CPU 費用。
- **判断事項**: セッション再開機能を持たないため、クライアントが再接続するたびに完全ハンドシェイクが発生する。接続元ごとの上限（既定 4）、同時計算数上限（既定 2）のパラメータ設定値が、想定する運用規模とトラフィック特性に適しているかの確認。

### 3. 証明書の更新運用とシステム時計（決定 2.1〜2.5）
- **内容**: ACME クライアントは内蔵されず、外部（certbot 等）が PEM ファイルを更新する運用となる。
- **判断事項**:
  - 秘密鍵ファイルのパーミッション管理（`0o077` 排除の運用手順）。
  - 証明書の有効期間判定に依存するシステム時計の同期・巻き戻り監視運用の確認。

### 4. 平文区間の非ループバック許可とマルチテナント脅威（決定 3）
- **内容**: 終端部品から後段への転送は平文＋PROXY v2 ヘッダーで行われる。
- **判断事項**:
  - 既定のループバック接続から非ループバックへの変更（`allow_non_loopback_upstream = true`）を許可する場合のネットワーク分離（専用 VPC / プライベートサブネット）の担保。
  - 同一ホスト上に信頼できない別プロセスが存在する場合、上流ポートへ直接接続して PROXY ヘッダーを偽装可能であるというアーキテクチャ上の限界の認識と許容。

### 5. 再開機能非対応による接続オーバーヘッド（決定 1）
- **内容**: 0-RTT およびセッション再開（チケット・PSK）を持たない。
- **判断事項**: セッションキャッシュを持たないことによるメモリ安全性と攻撃面削減のメリットに対し、頻繁な接続確立を行う HTTP クライアントに対するレイテンシ影響の確認。

### 6. 長時間ファジング（ADR 0020 G3 確認項目）
- **内容**: G2 においては各段で負の例および短時間のファジングを実施済み。
- **対応**: G3 レビュー前の必須項目として、全ファジング対象（ClientHello 解析、レコード層再構成、PEM/DER/X.509 解析）について 1 時間以上の長時間ファジングを実施し、所有者へ結果を報告する。

### 7. 外部公開可否の最終決定
- **結論**: **G2 は外部公開を承認しない**。本検証記録および G3 レビュー結果に基づき、所有者（goodnasubi）が外部公開の可否を最終決定する。
